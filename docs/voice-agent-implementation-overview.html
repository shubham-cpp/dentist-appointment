System shape

The dashboard uses one internal control contract. The selected runtime changes behind that contract. Both new candidates use the same scheduling rules and result shape.

  1. 1DashboardStarts, polls, and stops one controlled attempt.
  2. 2Runtime switchSelects the current gateway, Twilio candidate, or Telnyx candidate.
  3. 3Call providerPlaces the test call and carries speech.
  4. 4Voice agentUnderstands the caller and chooses a narrow tool.
  5. 5Local authorityChecks identity, slots, confirmation, and writes.
  6. 6Demo resultUpdates only the fictional appointment and dashboard.
Why the split matters. The model handles language. The application owns facts and changes. A model reply cannot create a valid appointment change alone.

What each path does

1. Current gateway

This is the checked-in baseline under src/voice-gateway. Its configuration still uses Twilio account fields and a local model endpoint.

  1. The dashboard creates a request ID and sends the fictional call context.
  2. The gateway takes a single-call lease before it creates a billable call.
  3. Twilio answers with ConversationRelay and opens a WebSocket to the gateway.
  4. The gateway receives final speech prompts and maps them to one intent.
  5. A fixed state machine writes the caller-facing reply.
  6. The gateway stores the final result. The dashboard then applies it once.

This design protects scheduling facts. It does not handle natural corrections or combined constraints well. That limit caused the new candidate work.

2. Improved Twilio candidate

This path keeps ConversationRelay for the telephone and speech pipeline. It replaces the fixed intent dialogue with a streaming model conversation.

  • The model keeps prior messages and responds to corrections or interruptions.
  • The model streams text back through ConversationRelay.
  • Five typed tools call the local scheduling authority.
  • The candidate records provider events, model output, tool calls, transcripts, and audio.
  • The dashboard keeps the same start, poll, stop, and result contract.

3. Telnyx managed candidate

This path moves speech recognition, dialogue, and text-to-speech into a Telnyx AI Assistant. The application still owns every scheduling decision.

  • Call Control Dial starts one call with an embedded assistant.
  • Dynamic variables carry the attempt ID, clinic name, patient name, and tool token.
  • Telnyx sends signed lifecycle events to the local gateway.
  • The assistant calls five synchronous scheduling webhooks.
  • Each webhook binds its bearer token to the active call.
  • The candidate stores evidence for later safety, latency, and voice review.
Earlier managed trial. Migration records describe an earlier nine-tool assistant and a later eight-tool trial. The current comparison uses five tools. This reduces model-controlled transitions.

The scheduling authority stays local

Both new candidates call the same authority in src/voice-experiment/scheduling-authority.ts. The provider and model cannot bypass it.

Tool Purpose Important rule
verify_identity Records confirmed, unclear, or wrong-person identity. No appointment facts before confirmation.
find_slots Returns filtered times from the fictional schedule. The model cannot invent a slot.
prepare_change Stores one reschedule or cancellation proposal. This step does not change the appointment.
commit_change Applies the prepared action. It needs explicit confirmation and a valid action token.
request_staff_follow_up Records a safe handoff. Use it when automation cannot continue safely.

What the agent can do

  • Understand normal patient language.
  • Ask one useful question.
  • Keep context after a correction.
  • Select a narrow tool.
  • Explain a returned result.

What the application must do

  • Protect identity and appointment facts.
  • Return real fictional availability.
  • Prepare the exact requested change.
  • Check confirmation and operation IDs.
  • Apply one idempotent result.

Safety boundaries in the demo

The implementation treats every phone call as a controlled experiment. These rules are part of the code, not only the prompt.

  • Fictional data onlyThe call can change only the demo appointment.
  • Local dashboard onlyThe server action rejects non-loopback dashboard origins.
  • Explicit billable actionThe interface shows a second confirmation before a call.
  • One active callA file lease blocks concurrent calls and adds a ten-minute cooldown.
  • Stable request IDsA retry can recover an uncertain start without a second local attempt.
  • Provider verificationTwilio and Telnyx callback paths verify provider signatures.
  • Bound tool accessTelnyx tools require a per-attempt token and matching call ID.
  • Idempotent changesAn operation ID can return its first result, but cannot run different input.
Production boundary. This demo does not prove HIPAA compliance. It does not use a real clinic schedule. Candidate recordings exist only for the fictional comparison and need a separate production policy.

In short

The work connects each phone provider to a controlled test system. It has swappable runtimes and local transaction rules.

The agent handles conversation while the application protects identity, availability, confirmation, and appointment changes.

The implementation is still experimental. Local safety is strong, but live voice evidence must choose the final runtime.
